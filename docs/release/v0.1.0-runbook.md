# TensorPlate v0.1.0 release runbook

This runbook owns the public `v0.1.0` release process. It is intentionally
split into two phases.

- Phase 1: the implementation PR creates release tooling and docs.
- Phase 2: after that PR is merged, a release owner cuts and publishes
  `v0.1.0` from a clean `release/v0.1.0` commit and annotated tag.

The Phase 1 PR is not the release.

## Required owners

Record sign-offs in a copy of
[`v0.1.0-signoff-template.md`](./v0.1.0-signoff-template.md).

| Role | Responsibility |
| --- | --- |
| Release owner | Drives the release branch, tag, GitHub Release, and evidence archive. |
| Runtime reviewer | Reviews C++ runtime, serving worker, version surfaces, and adapter risk. |
| Agent CLI reviewer | Reviews agent, CLI, deploy, rollback, doctor, and status/log command posture. |
| Packaging reviewer | Reviews `.deb` artifacts, package metadata, maintainer scripts, and checksums. |
| Validation reviewer | Reviews E15 release gate and E16 clean-room evidence. |
| Security reviewer | Reviews `SECURITY.md`, local endpoint posture, and advisory risk. |
| Docs reviewer | Reviews install guide, quickstart, release notes, and known limitations. |

## Phase 1: implementation PR

The implementation PR may add or update:

- `tools/release/tensorplate-release.sh`
- docs under `docs/release/`
- public install and quickstart docs under `docs/install/`
- clean-room validation procedure under `docs/validation/`
- support posture in `README.md` and `SECURITY.md`
- changelog notes for release tooling

Allowed validation during the implementation PR:

```bash
tools/release/tensorplate-release.sh --help
tools/release/tensorplate-release.sh prepare --version 0.1.0 --dry-run
test/release/run.sh
```

Forbidden in the implementation PR:

- Creating `release/v0.1.0`.
- Removing development suffixes as a final release commit.
- Creating `v0.1.0-rc.N` or `v0.1.0`.
- Publishing a GitHub Release.
- Treating local build output as public release evidence.

## Phase 2: final release operation

### 1. Confirm prerequisites

The release owner stops immediately unless all prerequisites are true:

- E15 release-gate decision is `pass` or signed `conditional-pass`.
- Required CI for the release commit is green.
- Security review is complete.
- Packaging artifacts can be built from the release commit.
- Public install guide and quickstart are reviewed.
- Clean-room validation target is ready: Jetson Orin Nano 8GB Super,
  JetPack 6.x / L4T 36.x, clean device state.
- No release blocker is open without a signed conditional pass.

### 2. Create or verify the release branch

```bash
git fetch origin
git switch --create release/v0.1.0 origin/develop
git status --short --branch
```

If `release/v0.1.0` already exists, verify it points at the reviewed
post-merge release baseline before continuing.

### 3. Prepare release metadata

Preview changes:

```bash
tools/release/tensorplate-release.sh prepare --version 0.1.0 --dry-run
```

Apply metadata changes only on the release branch:

```bash
tools/release/tensorplate-release.sh prepare \
  --version 0.1.0 \
  --execute \
  --confirm PREPARE-v0.1.0
```

Review that only these files changed:

- `CMakeLists.txt`
- `Cargo.toml`
- `Cargo.lock`
- `vcpkg.json`
- `packaging/VERSION`
- `packaging/debian/changelog`
- `CHANGELOG.md`

Commit the release metadata update after review.

### 4. Build artifacts

Build from the release commit:

```bash
cargo build --release --bin tensorplate-agent --bin tensorplate-observability --bin tensorplate
cmake --build build/release --target tensorplate-serving
./packaging/scripts/build-deb.sh
```

Collect the six required `.deb` assets under `dist/release/v0.1.0/`.
Artifact names and manifest rules are defined in
[`v0.1.0-artifacts.md`](./v0.1.0-artifacts.md).

### 5. Generate manifest and checksums

```bash
tools/release/tensorplate-release.sh manifest \
  --version 0.1.0 \
  --tag v0.1.0 \
  --artifacts-dir dist/release/v0.1.0 \
  --manifest dist/release/v0.1.0/tensorplate-v0.1.0-artifacts.json \
  --checksums dist/release/v0.1.0/SHA256SUMS
```

Review the manifest for package names, versions, architecture, release
commit, source tag, checksums, and validation links.

### 6. Record sign-off

Copy the sign-off template to the evidence directory:

```bash
mkdir -p dist/release/v0.1.0
cp docs/release/v0.1.0-signoff-template.md dist/release/v0.1.0/signoff.md
```

Fill the copied file with final decisions. The release script rejects
`TODO`, `TBD`, `PLACEHOLDER`, `BLOCKED`, missing reviewers, missing E15
gate, or a decision other than `pass` / `conditional-pass`.

Create the evidence handoff from
[`v0.1.0-evidence-template.md`](./v0.1.0-evidence-template.md) and keep it
updated as preflight, tag, GitHub Release, and clean-room validation
complete.

### 7. Run preflight

```bash
tools/release/tensorplate-release.sh preflight \
  --version 0.1.0 \
  --artifacts-dir dist/release/v0.1.0 \
  --manifest dist/release/v0.1.0/tensorplate-v0.1.0-artifacts.json \
  --checksums dist/release/v0.1.0/SHA256SUMS \
  --signoff dist/release/v0.1.0/signoff.md \
  --report dist/release/v0.1.0/preflight.md
```

Preflight must pass before final tag creation. A failure is actionable and
must be fixed in the owning area, not patched around in release
automation.

### 8. Create the annotated tag

For a release candidate, use the same preflight inputs and create the next
RC tag:

```bash
tools/release/tensorplate-release.sh tag \
  --version 0.1.0 \
  --rc 1 \
  --artifacts-dir dist/release/v0.1.0 \
  --manifest dist/release/v0.1.0/tensorplate-v0.1.0-artifacts.json \
  --checksums dist/release/v0.1.0/SHA256SUMS \
  --signoff dist/release/v0.1.0/signoff.md \
  --confirm CREATE-v0.1.0-rc.1
```

Failed RCs are never retagged. Fix the blocker, rebuild artifacts,
regenerate manifest/checksums, rerun required validation, and create the
next `v0.1.0-rc.N`.

For the final release:

```bash
tools/release/tensorplate-release.sh tag \
  --version 0.1.0 \
  --final \
  --artifacts-dir dist/release/v0.1.0 \
  --manifest dist/release/v0.1.0/tensorplate-v0.1.0-artifacts.json \
  --checksums dist/release/v0.1.0/SHA256SUMS \
  --signoff dist/release/v0.1.0/signoff.md \
  --confirm CREATE-v0.1.0
```

Inspect tag metadata:

```bash
git show v0.1.0
```

Push the branch and tag only after review:

```bash
git push origin release/v0.1.0
git push origin v0.1.0
```

### 9. Create the GitHub Release draft

Generate the guarded draft command first:

```bash
tools/release/tensorplate-release.sh publish \
  --version 0.1.0 \
  --tag v0.1.0 \
  --artifacts-dir dist/release/v0.1.0 \
  --manifest dist/release/v0.1.0/tensorplate-v0.1.0-artifacts.json \
  --checksums dist/release/v0.1.0/SHA256SUMS \
  --release-notes docs/release/v0.1.0-release-notes.md \
  --dry-run
```

After review, create the draft:

```bash
tools/release/tensorplate-release.sh publish \
  --version 0.1.0 \
  --tag v0.1.0 \
  --artifacts-dir dist/release/v0.1.0 \
  --manifest dist/release/v0.1.0/tensorplate-v0.1.0-artifacts.json \
  --checksums dist/release/v0.1.0/SHA256SUMS \
  --release-notes docs/release/v0.1.0-release-notes.md \
  --execute \
  --confirm PUBLISH-v0.1.0
```

The draft must contain the `.deb` packages, manifest, checksums, release
notes, install guide, validation links, supported hardware/OS statement,
known limitations, support policy, security policy, and rollback guidance.

### 10. Run clean-room validation from GitHub Release assets

Run the procedure in
[`docs/validation/v0.1.0-clean-room-release-smoke.md`](../validation/v0.1.0-clean-room-release-smoke.md).
The validation must download the GitHub Release assets and verify
checksums before install. Local source-tree binaries or local package
build directories invalidate the evidence.

Record the result in the E16 clean-room report. If the result is `block`,
do not publish the release. If the result is `conditional-pass`, the risk,
mitigation, owner, and follow-up issue must also appear in release notes.

### 11. Publish and announce

Publish the GitHub Release only after clean-room validation is accepted.
Then publish the announcement using the release notes as the source of
truth. The announcement must not claim support for Kria, hosted platform
connectivity, container-only install, unsupported model classes, or
unvalidated hardware.

### 12. Monitor after release

For the first release window:

- Watch install failures and `tensorplate doctor` reports.
- Triage security reports privately according to `SECURITY.md`.
- Track artifact download or checksum problems.
- Open follow-up issues for conditional risks and docs corrections.
- Use the hotfix process in
  [`v0.1.0-post-release.md`](./v0.1.0-post-release.md) for supported
  patch releases.

## Stop-the-release criteria

Stop and mark the release blocked if any item is true:

- E15 gate is not pass or signed conditional-pass.
- Required CI is unavailable or not green.
- The release branch has unreviewed commits.
- Version metadata or changelog is inconsistent.
- A final `v0.1.0` tag already exists.
- Artifacts are missing, checksums mismatch, or manifest commit/tag data
  does not match the release.
- Required sign-off is missing.
- Clean-room validation uses local build-tree paths.
- Clean-room install, doctor, service start, deploy, inference, status,
  logs, metrics, or rollback fails without signed conditional-pass.
- Release notes overstate supported hardware, model classes, backends, or
  security posture.
