# TensorPlate v0.2.1 release notes

> Draft for the final release owner. Do not publish the final `v0.2.1`
> release until the tag, artifacts, checksums, Production-row lifecycle
> evidence, and sign-off are complete. Release candidates publish without
> that evidence on purpose — see "Validation status" below.

TensorPlate v0.2.1 makes **the platform support matrix an artifact the
software reads**, not a table in a document. A schema-first registry under
`config/platform/` names every machine TensorPlate claims to run on; the
agent, `tensorplate doctor`, and the observability service all answer
platform questions from that one registry, and a deploy is admitted or
refused against the row the running machine actually resolves to.

Two new runtime targets ride on that work: a complete **Ubuntu 24.04
x86_64** runtime package set, and a **macOS Apple Silicon** appliance
installed from the Homebrew tap. Before this release both architectures
received the operator CLI only. A final tag is necessary but not
sufficient for tap availability — see "Channel availability" below.

```sh
# which supported machine is this, and what will it admit?
tensorplate doctor

# the same answer as structured output
tensorplate doctor --output json
```

`doctor` gains a host section, and three findings inside it:
`platform_row`, the one row the machine resolves to and its support level;
`accelerator_facts`, the accelerator SKU and device count; and
`model_class_rows`, which model classes that row serves and at what level.
Those three strings are the finding `id`s `--output json` emits. The host's
own identity is reported by the older `host_facts` and `host_os` findings,
which the section now groups rather than introduces.

## Added in this release

- **Platform support row registry** — `config/schemas/platform_support_row.json`
  and the committed rows under `config/platform/`: thirty rows covering
  Jetson Orin, Apple silicon, Ubuntu x86_64 CPU-only, and NVIDIA
  L4 / A100 / H100 / RTX PRO 6000 hosts — four Production, twenty-two
  Preview, and four Planned, the last defined but carrying no support
  claim. A new `tensorplate-platform` workspace crate owns platform
  identity, registry loading, and the query API that resolves a detected
  machine to exactly one row; exact accelerator rows take precedence over
  compatibility envelopes.
- **Detection that reads the machine** — CPU architecture and vendor, OS
  identity, Apple chip identity and unified-memory size from `sysctl`, and
  the PCI bus, so an accelerator that is physically present can be told
  from one that is absent. Discrete NVIDIA accelerators resolve by exact
  SKU. On a Compute Engine instance, detection no longer needs the metadata
  service on every start, and startup retries detection on a bounded budget
  rather than refusing deploys for the life of the process.
- **`tensorplate doctor` names the row the machine is** — a host section
  reporting what the machine says about itself rather than what the binary
  was compiled for, a `platform_row` finding resolving the machine to one
  row and reporting its support level, an `accelerator_facts` finding
  reporting SKU and device count including mixed-SKU and partitioned sets,
  a `model_class_rows` finding naming which model classes that row serves
  and at what level, and per-row memory telemetry in the row's own memory
  model.
- **Deploy admission against the matched row** — a deploy is refused before
  anything is staged when the machine cannot honour it: a partitioned
  accelerator, a GPU host whose driver is missing or broken, or a bundle
  whose backend package requirements the matched row does not satisfy.
  How strictly a machine is judged is an explicit, reported **admission
  posture** rather than one policy applied everywhere. Refusals carry a
  typed reason from a vocabulary frozen for this release and documented in
  [`docs/platform/support-reasons.md`](../../platform/support-reasons.md),
  checked as a cross-language contract between the Rust agent and the
  Python sidecar.
- **Accelerator topology** — support rows declare an accelerator
  `device_count`, bundle manifests may declare an `accelerator_requirements`
  block with a `replicas` or `device_set` mode, and worker supervision
  accepts a device pin that sets `CUDA_VISIBLE_DEVICES` at launch. Changing
  or removing a pin for a running deployment stops the old worker before
  launching its replacement. Multi-device memory ceilings use the smallest
  known device capacity, and mixed accelerator SKUs are refused regardless
  of device order.
- **Ubuntu 24.04 x86_64 runtime** — releases now publish a complete x86_64
  runtime package set: agent, serving worker, observability service,
  operator CLI, and the `tensorplate` metapackage. The installer validates
  the host OS per architecture, accepting Ubuntu 24.04 on x86_64 alongside
  JetPack 6.x / L4T 36.x on arm64.
- **macOS Apple Silicon appliance** — the Homebrew tap now covers agent,
  serving worker, CLI, observability, and the Python/PyTorch backend, with
  launchd service definitions, prefix-rendered configs, and a control
  socket confined to the installing user (`0700` runtime directory, `0600`
  socket). The Python/PyTorch sidecar probes the configured Apple
  accelerator runtime before SmolVLA model dependencies or weights load.
- **Lifecycle validation harnesses and evidence machinery** — native
  harnesses for the Jetson Orin Nano row, the Apple M1 Pro row, and the
  Ubuntu x86_64 cloud rows, each writing the same schema-checked lifecycle
  report across eight canonical stages (install, upgrade, deploy-smoke,
  status-logs, rollback, restart, crash-loop, offline). Evidence is scanned
  for identifiers before it can be published, and the release workflow gates
  on evidence completeness for Production rows.

Documentation: the support matrix is projected from the registry into
[`docs/release/support-matrix.md`](../support-matrix.md) — regenerated, not
hand-edited. Validation runbooks are in
[`docs/validation/physical-row-runbooks.md`](../../validation/physical-row-runbooks.md),
[`docs/validation/cloud-row-runbooks.md`](../../validation/cloud-row-runbooks.md),
and [`docs/validation/macos-homebrew-lifecycle.md`](../../validation/macos-homebrew-lifecycle.md).

## Validation status

**The four Production rows in this release carry no recorded lifecycle
evidence yet.** All four — `jetson-orin-nano-8gb-jp62`,
`macos26-m1pro-16gb`, `ubuntu2404-x86-l4-g2s8`, and
`ubuntu2404-x86-h100-80g-a3hg1` — are `provenance: spec_authored`: their
rows describe hardware the release is written for, and nobody has yet run
the lifecycle harness against this version on that hardware and filed the
result. Nothing in these notes should be read as a report of a run on an
L4, an H100, a Jetson, or an M1 Pro.

This is the expected state for a release candidate, and it is enforced that
way. The release workflow's evidence gate blocks a **final** tag until every
Production row carries a recorded, schema-valid, passing lifecycle report
whose subject names this version and whose stage logs exist. Candidates are
not gated, because the evidence can only come from one: the harnesses
validate published candidate artifacts, and evidence gathered on
`v0.2.1-rc.N` is filed against the `0.2.1` it stands for. The final tag is
where the support claim is made, so the final tag is where it is enforced.

What that evidence covers is the appliance lifecycle: install, upgrade,
deploy admission, status and logs, rollback, restart, crash-loop recovery,
and offline operation. Its deploy-smoke stage is not the same thing on
every row, and what a passing report does and does not claim differs with
the harness that produced it:

- **Ubuntu L4 and H100 cloud rows** — the smoke bundle selects the
  device-neutral `fixture` backend profile. It exercises admission, worker
  supervision, and the sidecar inference path against the real installed
  appliance, and it executes **no accelerator kernel**; there is no CUDA
  fixture backend to select yet. A passing lifecycle report on the L4 or
  the H100 row is therefore not evidence that the GPU computed anything,
  and a final `v0.2.1` must not be read as GPU validation on those rows.
- **macOS M1 Pro row** — the smoke bundle's model artifact is checked to
  declare `backend_profile=mps_fixture` on `device=mps`, and the backend
  it selects performs and synchronizes a PyTorch tensor operation on
  `mps` while loading. The deployment cannot become active if MPS is
  unavailable or that operation fails, so this row's harness does cover an
  accelerator operation — one tensor op at load, not a model workload and
  not a performance result.
- **Jetson Orin Nano row** — the smoke deploys against the `tensorrt`
  backend and checks a serving round trip through the agent-discovered
  endpoint of the active worker, against an identity engine that returns
  its input. That the serving path works end to end is the whole claim:
  the harness records `compute_claim: none` and asserts nothing about
  accuracy, speed, or compute.

None of the three is a model-quality or performance result, and none of
them has been recorded for this version on that hardware yet.

The two GPU Production rows also carry narrow model-class claims: the L4
row serves `chunked_policy` at Preview, and the H100 row serves no model
class at all. Production on those rows is a claim about the platform row
and its gating, not about a served workload.

Support level is a claim about intent and gating, not a record of a run.
Reading the current state of the gate is a command, not a document:

```console
$ tools/release/check-evidence-bundles.sh --version 0.2.1
```

## Limitations

- **Multi-GPU is not supported in this release.** Multi-device rows are
  published at Preview so the topology can be described and detected, but a
  bundle manifest requesting `device_count` greater than one is refused
  rather than served on fewer devices than it asked for. Both `replicas`
  and `device_set` modes are frozen in the manifest contract; neither is
  executable here.
- **Release candidates are not published to the stable channels.** The APT
  repository, PyPI, and the Homebrew tap all publish on a final tag only,
  so `apt install`, `pip install tensorplate-python`, and
  `brew install tensorplate/tap/tensorplate` do not resolve a candidate.
  A candidate is still installable, which is how it gets validated in the
  first place, but the three routes do not carry the same guarantees:
  - **Debian hosts** — `install.sh --version v0.2.1-rc.N` installs the
    candidate's attached package set (the installer reads the candidate's
    own artifact manifest, so it picks up the `0.2.1~rc.N` package
    versions), and `--local-artifacts DIR` installs from an
    already-downloaded asset directory. These are release assets covered
    by `SHA256SUMS` and the cosign bundle over it.
  - **SDK** — `pip install` the attached
    `tensorplate_python-0.2.1rcN-py3-none-any.whl` directly. Also a
    checksum-covered, cosign-signed release asset.
  - **macOS** — **not a signed route.** Render the six candidate formulae
    locally and stage them into the tap checkout, per
    [`docs/validation/macos-homebrew-lifecycle.md`](../../validation/macos-homebrew-lifecycle.md);
    the tap must already be tapped and its checkout clean, and the
    candidate is then installed by tap-qualified name
    (`brew install --formula <tap>/tensorplate`) so the metapackage's
    by-name dependencies resolve to the staged candidate formulae. The
    formulae build from the tag's GitHub-generated source archive
    (`.../archive/refs/tags/<tag>.tar.gz`), which is **not** a release
    asset: it is absent from the Assets list below, from `SHA256SUMS`,
    and from the cosign bundle. The digest the formula pins is one the
    operator computes locally from the downloaded archive. That is the
    supported route for validating a candidate on macOS; only final
    releases reach the tap.
- **The macOS Homebrew formulae carry placeholder release data** — a
  `v0.0.0` source URL and a zero digest — until a tag exists to render them
  against. The workflow renders them on a final tag when the Homebrew
  publish channel is configured; the committed templates are not
  installable as they stand. The tap therefore carries the macOS appliance
  only once `v0.2.1` is final and that tap PR has merged, and a candidate
  is installed from formulae rendered locally against its own archive, as
  described above. The final route builds from the same GitHub-generated
  source archive as the candidate route:
  `tools/release/publish-homebrew-formula.sh` downloads it and computes
  the digest itself. No cosign signature covers the macOS source path at
  either stage.
- **amd64 upgrade and rollback evidence needs two release candidates.**
  Those stages need a published, signed baseline whose amd64 runtime set is
  older than the candidate's, and `v0.1.x` published only the CLI for that
  architecture. The first candidate published with an amd64 runtime set
  under the names its manifest lists is therefore the first release that
  can serve as one, and the upgrade path off it can only be exercised by
  the candidate after it. `v0.2.1-rc.1` cannot serve: its manifest and
  signed `SHA256SUMS` named each package with a `~` that GitHub serves as
  `.`, and its release and tag are no longer on GitHub. Without
  `--baseline-assets-dir` the cloud harness skips both stages and names
  the option in the skip reason.
- The Jetson harness upgrades from `v0.1.5`, the published arm64 baseline;
  that path is unaffected by the amd64 limitation above.
- `provenance: spec_authored` rows are not a validation record. See
  "Validation status".

## Channel availability

A final tag starts the stable-channel publishes; it does not by itself
complete them. Each channel has an additional gate, and every publish job
runs in a reviewer-gated environment:

| Channel | Also requires | "Done" means |
| --- | --- | --- |
| APT | `TP_APT_REPO_DEST` configured | the repository is published |
| PyPI | `PUBLISH_SDK_TO_PYPI=true` | the wheel and sdist are uploaded |
| Homebrew tap | `PUBLISH_HOMEBREW_FORMULA=true` and a tap-scoped token | a formula-graph PR is **opened with auto-merge armed** |

The tap case is the one to read carefully: the release workflow's job
succeeds when the PR exists, not when it merges. The tap's own CI (audit,
build-from-source, and `brew test` on Apple Silicon) gates that merge, so
`brew install tensorplate/tap/tensorplate` resolving the new version is
eventually consistent with the tag, not simultaneous with it.

The negative claims elsewhere in these notes — that candidates reach none
of these channels — hold regardless: a final tag is a necessary condition
for every one of them.

## Fallback artifact source

GitHub Release assets remain the checksum-covered, cosign-signed source of
truth: every `.deb`, the SDK wheel and sdist, `install.sh`, the artifact
manifest, `SHA256SUMS`, and `SHA256SUMS.cosign.bundle` are attached to this
release, and the APT repository is reproducible from them. Verification
commands: [`SECURITY.md`](../../../SECURITY.md) and
[`docs/install/external-install.md`](../../install/external-install.md).

## Supported environment

- Jetson Orin Nano 8GB Super hardware floor; JetPack 6.x with L4T 36.x;
  `arm64` runtime packages attached to this release, and via the APT
  channel once the release is final and that channel is configured.
- Ubuntu 24.04 on `x86_64`, with a complete runtime package set for that
  architecture. The Production rows on that OS are the single-accelerator
  L4 and H100 cloud rows, each scoped to the machine shape the matrix
  names; a CPU-only Ubuntu 24.04 host resolves to a Preview row.
- macOS 26 on Apple silicon, installed from the Homebrew tap once the
  release is final, the tap channel is configured, and the tap PR has
  merged.
- `install.sh` validates the host OS per architecture and accepts only
  those two: JetPack 6.x / L4T 36.x on `arm64`, Ubuntu 24.04 on `x86_64`.
  A Preview row the platform layer can resolve is not therefore a host
  this release installs on — the Ubuntu 22.04 `x86_64` CPU-only row is
  one the installer refuses.
- The SDK is a pure-Python client (`py3-none-any`) for Python 3.10+ on any
  platform, targeting a reachable TensorPlate serving endpoint.
- Local-only default endpoints through Unix sockets and loopback.

The authoritative per-row list, with support levels, is
[`docs/release/support-matrix.md`](../support-matrix.md).
