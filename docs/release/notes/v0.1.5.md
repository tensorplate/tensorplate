# TensorPlate v0.1.5 release notes

> Draft for the final release owner. Do not publish until the `v0.1.5`
> tag, artifacts, checksums, validation evidence, clean-room evidence, and
> sign-off are complete.

TensorPlate v0.1.5 adds **SSH device enrollment**: a local-first device
registry and remote command routing so an operator running the CLI (macOS or
Ubuntu) can enroll an SSH-reachable Jetson once and then run normal
`tensorplate` commands against it — including deploy — with nothing exposed on
the network beyond OpenSSH. The agent and serving worker stay loopback/local
only; the wire protocol (`schema_version` `0.1`) is unchanged, and existing
local and `--profile`/`--agent-url` workflows are unchanged from v0.1.4.

```sh
# once
tensorplate device add orin-lab --ssh reid@orin-lab.local
tensorplate device use orin-lab

# then normal commands run on the device
tensorplate status
tensorplate deploy ./bundles/yolov8n
tensorplate logs --tail 100
```

Enrollment follows the MicroK8s model: install the packages, add the SSH user
to the `tensorplate` group (`sudo usermod -aG tensorplate <user>`, then
re-login), and enroll. `device add` verifies reachability up front and refuses
to save a device it cannot actually use, with actionable hints (including an
explicit "upgrade the device to >= 0.1.5" when the remote is older).

## Added in this release

- **Local device registry and the `tensorplate device` command group**
  (`add`, `list`, `use`, `sync`, `prune`, `remove`, `rename`) — an atomic,
  human-inspectable JSON file (`$TENSORPLATE_DEVICE_REGISTRY`, else
  `$XDG_CONFIG_HOME/tensorplate/devices.json`, else
  `~/.config/tensorplate/devices.json`) holding device access metadata and
  cached facts; never SSH keys, passwords, or agent secrets.
- **SSH remote command routing** — with a device selected (`--device <name>`
  or a `device use` default), `status`, `rollback`, `logs`, `doctor`, `infer`,
  `version`, and `deploy` run against the device over plain OpenSSH with a
  forced remote `--local` and structured, POSIX-quoted arguments. Selection
  precedence: `--local` > `--device` > `--profile`/`--agent-url` > registry
  default > local. JSON output keeps the stable envelope and adds an optional
  top-level `device` object; the CLI fails closed on SSH failure, malformed
  remote output, or protocol-version mismatch, mirroring the remote exit code.
- **Remote deploy staging** — `deploy <bundle>` under `--device` copies the
  bundle to the device's import dir (`/var/lib/tensorplate/bundles/import`,
  created by packaging as sticky/group-writable `1775`) via `rsync` (`scp`
  fallback), then runs the device-side deploy transaction, so verification,
  promotion, and rollback keep their local guarantees. `device prune`
  reclaims import storage with an explicit policy (`--keep` /
  `--older-than`) and always protects the active deployment's import.
- **Run-as execution and enrollment preflight** — devices enrolled with
  `--run-as <user>` route through structured, non-interactive
  `sudo -n -u <user> -- …` after the remote binary is vetted (absolute,
  root-owned, not group/other-writable). `device add` preflights
  reachability by default (`--no-verify` to skip); `device sync` refreshes
  cached version/protocol/last-seen facts non-destructively.
- **Group-accessible agent socket** — the agent control socket now binds
  `0o660` (the documented `SOCKET_0660`) instead of `0o600`, so CLI users
  reach the agent via `tensorplate`-group membership without per-user sudoers
  rules. Access stays confined to the non-root `tensorplate` user and the
  five control operations; `--run-as` remains as a fallback for sites that do
  not grant group membership. The CLI also now validates agent response
  protocol versions through the shared version check, surfacing a typed
  incompatibility error instead of a generic parse failure.

## Limitations

- One device at a time: the registry selects a single default device; fleet
  fan-out, hosted relays, and cloud device inventory remain non-goals.
- Remote routing requires tensorplate >= 0.1.5 on the device (the remote
  invocation contract does not exist in older releases; enrollment detects
  and reports older devices). The device-side agent still serves loopback
  only; nothing new listens on the network.
- `logs --follow` is not supported over `--device`; `infer` over `--device`
  pipes stdin through the remote CLI (a low-latency serving tunnel remains a
  possible future opt-in).
- The invite/join pairing flow (`agent invite` / `device join`) is design
  work only and not shipped; SSH remains the transport authorization
  boundary.
- Upgrading the device package is what creates the import dir and the
  group-accessible socket; on older installs `deploy` over `--device` fails
  closed with setup hints until the upgrade is applied.

## Fallback artifact source

The SDK wheel and sdist are attached to this GitHub Release and covered by
the same `SHA256SUMS` and `SHA256SUMS.cosign.bundle` as the runtime packages —
use this for checksum-verified or air-gapped installs. Verification commands:
[`SECURITY.md`](../../../SECURITY.md) and
[`docs/install/external-install.md`](../../install/external-install.md).

## Supported environment

- Runtime targets are unchanged from v0.1.4: Jetson Orin Nano 8GB Super
  hardware floor; JetPack 6.x with L4T 36.x; `arm64` runtime packages via the
  APT channel or attached to this GitHub Release; `amd64` CLI-only package;
  macOS Apple Silicon CLI via Homebrew.
- SSH device enrollment requires OpenSSH client-side (macOS/Linux operator
  host) and an SSH-reachable device on the same network; `rsync` is used for
  deploy staging when available, with `scp` as the fallback.
- The SDK is a pure-Python client (`py3-none-any`) for Python 3.10+ on any
  platform, targeting a reachable TensorPlate serving endpoint.
- Local-only default endpoints through Unix sockets and loopback.
