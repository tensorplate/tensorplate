# Golden output fixtures and tolerances

> **Status:** V01-E05-F06-T02. Authored before any large fixture artifact
> lands; the host CI fixtures and the Jetson HIL fixtures will follow as
> separate, scope-disciplined drops.

This document defines what a golden-output fixture means for each
v0.1.0 execution-backend adapter, how each fixture is generated, what
its expected output is, and what tolerance is acceptable. The goal is
to make adapter correctness checkable through a stable, reproducible
artifact rather than a one-off PR.

The fixtures live (or will live) under `test/models/` and are wired
into:

- Host-CI tier (T2 / T3): runs on every PR.
- Jetson HIL tier (T4): runs on the v0.1.0 validation device.
- Release-gate tier: blocks v0.1.0 freeze on Orin Nano 8GB Super
  validation.

## TensorRT vision golden fixture

**Source.** Public PyTorch / ONNX small detector or classifier
(candidates: MobileNetV3-small ImageNet classifier, MobileNet-SSD
detector with reduced input size, or a synthetic linear network we
generate from a fixed seed so the fixture is fully reproducible).

**Preprocessing.** Documented in the fixture's `README.md`: input
resolution, channel order (RGB vs. BGR), normalization mean/stddev,
data type after preprocessing (typically `float32` or `int8` for the
INT8 calibrated profile).

**Expected output.** Top-1 class index plus the raw score for the
classifier, or top-3 bounding boxes + confidences for the detector.
The expected values come from the source PyTorch model on CPU running
the same preprocessing pipeline; the generator script writes them to
the fixture directory so the test only has to compare.

**Tolerance.**
- FP32: `atol=1e-5`, `rtol=1e-5`.
- FP16: `atol=1e-2`, `rtol=1e-2`.
- INT8: top-k label match required; logits compared only with
  `atol=0.1` because INT8 quantization changes magnitudes.

**Where it runs.** Orin HIL tier (T4); host CI skips when TensorRT or
the engine file is absent. The host-CI run of the adapter T1 tests
asserts capability publication and that load-without-SDK surfaces
`Error::Code::Unsupported`.

## LibTorch exported-graph fixture

**Source.** Small `torch.jit.script` or `torch.jit.trace` artifact
generated by a checked-in script (`test/models/libtorch/generate.py`,
landing alongside V01-E05-F03-T03). The script pins the PyTorch
version it requires and writes the resulting `.pt` file plus an
`expected.json` next to it.

**Expected output.** Forward pass on the same inputs the script
records; the fixture stores both inputs and outputs as float32 arrays.

**Tolerance.** `atol=1e-5`, `rtol=1e-5` for FP32; FP16 / BF16 follow
the rules above.

**Where it runs.** Host tier (T2 / T3) when `Torch_DIR` is configured.
When LibTorch is absent the adapter T1 tests still assert capability
publication, the no-SDK `Unsupported` path, and the explicit
"`backend_hint: python_pytorch` never silently redirects to libtorch"
property.

## Python/PyTorch sidecar fixtures

**Fixture backend (already landed).** The dependency-free
`FixtureBackend` (see
`backends/python_pytorch/src/tensorplate_pytorch_backend/backends/fixture.py`)
echoes each input tensor back as `echo_<name>` with the same metadata
and payload bytes. The T2 integration test in
`test/integration/python_pytorch_adapter_test.cpp` and the V01-E05-F06
real-adapter contract test in
`test/contract/real_adapter_conformance_test.cpp` run the full
`ExecutionSession` lifecycle against this backend on every PR.

The `FixtureBackend` is sufficient to exercise:
- named multi-input requests (V01-E04 NVI validation),
- named outputs with explicit metadata,
- async-method-shape coverage (the sidecar protocol accepts
  `infer_async`, while the C++ `ExecutionSession` adapter returns typed
  `Unsupported` until V01-E06 provides result delivery),
- exact bytewise correctness of the input/output round-trip,
- failure-injection paths via the `fail_load` / `fail_prime` /
  `fail_infer` hooks (covered in
  `tests/test_failure_injection.py`).

**SmolVLA bundle fixture (V01-E15).** The end-to-end SmolVLA
validation on Jetson Orin Nano 8GB Super lives in V01-E15. The
fixture's required shape is documented in the v0.1.0 roadmap and in
`tensorplate-internals/planning/v0.1.0/v0.1_E5.md`: named inputs
(e.g. `image_front`, `image_wrist`, `state`, `instruction`) plus a
named chunk-shaped action output. The fixture is too large to be
checked in; the V01-E14 packaging work covers the install path for
the SmolVLA artifact under `backends/python_pytorch/` per the closed
v0.1.0 decision.

## How tolerances are surfaced

Each fixture directory carries an `expected.json` with:

```json
{
  "fixture_name": "...",
  "expected_outputs": [
    { "name": "out0", "dtype": "float32", "shape": [...], "values_b64": "..." }
  ],
  "tolerance": { "atol": 1e-5, "rtol": 1e-5 }
}
```

A shared C++ helper (lands with the first real golden fixture) reads
the JSON and asserts each output element-wise. The helper is part of
`test/contract/` so every adapter that ships a fixture uses the same
comparison code.
