# `test/packaging/`

packaging verification suite.

## What lives here

| File | What it asserts |
| --- | --- |
| `verify_layout.sh` | Stages the packaging install layout under a tempdir using the shared `packaging/scripts/install-paths.sh` helper and asserts every documented directory and config file has the documented permissions. Asserts that no directory ends up world-writable. |
| `verify_debian_metadata.sh` | Lints the debhelper-style metadata under `packaging/debian/`: every binary package declared in `control` has an `*.install` manifest, `/etc` config payloads rely on debhelper's single auto-generated conffile list, every maintainer script is executable, and only `tensorplate-agent` and `tensorplate-observability` ship a systemd unit. |
| `verify_apt_source.sh` | Lints the `tensorplate-apt-source` bootstrap package: arch `all` with no runtime dependencies, installs exactly the archive keyring and the Deb822 source, stable versionless `https://packages.tensorplate.com/apt` URI signed by the shipped keyring, fail-closed `postinst` that never runs `apt update` or touches runtime state, keyring dearmor wiring in `debian/rules`, and the staging-placeholder release guard in the release tooling. |
| `verify_metapackage.sh` | Lints the `tensorplate` runtime metapackage: `Architecture: any` (built once per runtime architecture, never `all`), `Section: metapackages`, strict-versioned depends on the full runtime set, Python backend suggested but never pulled in, no dependency on the apt bootstrap package, no payload or maintainer scripts, and release tooling carries it into assets/manifest/verification. |
| `verify_ready_check.sh` | Runs `tools/validation/tensorplate-ready-check.sh` against known-good and known-bad source/keyring fixtures (missing keyring, armored keyring, version-pinned URI, Signed-By mismatch) and asserts the correct verdict. |
| `verify_systemd_units.sh` | Parses `packaging/debian/*.service` and asserts the v0.1.0 invariants: `User=tensorplate`, `Group=tensorplate`, loopback-only `ReadWritePaths=`, hardening directives present, no `tensorplate-serving.service`. |
| `verify_lifecycle_scripts.sh` | Runs `version-utils.sh` and `upgrade-preflight.sh` against known-good and known-bad config fixtures and asserts each returns the correct exit code. |
| `verify_lifecycle_state_guard.sh` | Binds the rollback's durable-state preservation guard across the two harnesses that hold it. `privileged_sha256`, `state_manifest`, `manifest_digest`, `capture_state_manifest` and `check_state_preserved` must each be defined exactly once in `tools/validation/ubuntu-l4-cloud-lifecycle.sh` and in `tools/validation/jetson-lifecycle.sh` -- counting every spelling bash accepts, a one-liner, the `function` keyword and a definition nested in another function included, because bash runs whichever definition it met last -- each body must parse on its own, and the two copies must be byte-identical. Every harness variable those bodies touch is derived from the bodies rather than listed, upper or lower case and through any expansion form (`${NAME-}`, `${#NAME}`, `${!NAME}`, bare arithmetic, `-v`, assignment), and must be bound on exactly one line in each file, the same line in both; a binding is any line outside the bodies that names it unexpanded, so a respelled definition or a caller's `local` that shadows it counts. The comments above the functions are not compared: they name device facts that legitimately differ. After binding the real pair it plants each kind of drift it refuses into copies of the two harnesses and runs itself against them; each must fail with exactly its own checks, and untouched copies must pass, so deleting any one rule fails the run. In `core` rather than `harness` because it drives no appliance -- a copy-paste divergence should fail in the fast job. What makes it worth having: only the cloud verifier drives this code against a stubbed appliance, so without it a fix or a tightening applied to one harness leaves the other's Production-row evidence weaker while reading as if it were not. |
| `verify_macos_homebrew_lifecycle.sh` | Syntax-checks the guarded M1 Pro Homebrew lifecycle harness, verifies its mutation opt-in, installed-agent exact-row assertion, owner-only `0700` runtime directory, and `0600` agent socket checks, and runs shellcheck when available. Lints the harness for assertions ending in `[[ ]]`, `(( ))` or `!` (macOS `/bin/bash` 3.2 does not apply errexit to the first two, and no bash to `!`), for `set +e` outside the exit cleanup, and for `run_stage` calls that are not top-level statements, and runs the real `run_stage` to show a failing body records no pass. Renders the agent's admission line from its format string for the exact-row pattern. Runs the extracted launchd-start, launchd crash-loop and status-logs stage bodies against a fake Homebrew prefix and CLI, requiring the log offsets taken before the services start and output written during the current run, including event-log rotation across `events.ndjson` and `events.1`, and checks the status-logs stage order, formula log paths, transcript allowlist, and that the runbook's macOS mapping names all eight canonical stages. Runs the launchd-start, launchd-restart, crash-loop and uninstall bodies against a fake launchd that holds each job under the label its keg plist carries, Homebrew 7's `sh.brew.<formula>` or an older Homebrew's `homebrew.mxcl.<formula>`; the harness may name no label prefix itself, and copies that hardcode one form must fail. Runs the harness's clean install, upgrade, graph removals, cleanup and exit against a fake Homebrew that drops a tap formula's trust on uninstall and trusts the formula `brew install` names, requiring the six formulae's per-formula trust to end as it began; copies without each trust restore must fail. The hardware run itself is manual. |
| `verify_macos_offline_runtime.sh` | Tests `tools/validation/macos_offline_runtime.py` and the harness's `offline-profile` and `offline-runtime` stages. On every host: profile rendering and its lint, which must refuse mutants including any added rule, plist derivation refusals, `launchctl print` and `lsof -F` parsing, the `sandbox_check` identity check (exited and unreaped processes) and discrimination controls, classification of probe outcomes recorded under the rendered profile and twelve mutants (among them TCP to any loopback port, TCP or UDP to any host on the serving ports, and binds on any port), a control required for every probe operation, and the doctor, status, deploy, inference and admission checks. Runs the extracted offline-runtime stage and cleanup against a fake Homebrew, launchd, process table and CLI (`fixtures/macos-offline/fake_host.py`) through a clean run under Homebrew 7 labels and under an older Homebrew's, a keg with no plist of either label form, delayed initial launchd PIDs, jobs that never acquire a PID, one run per injected fault, purges from partial launchd states, including sandboxed jobs under either label, with the kegs removed, and jobs an older Homebrew left under its label, and INT, TERM and HUP delivered mid-stage, again during the restore, after the terminal hangs up or its output pipe's reader exits, and during the baseline restore, requiring a fail row and normal launchd supervision afterwards; startup polls each job at most 30 times with one-second waits between pending reads, and the final same-PID and one-launchd-run checks remain mandatory. A cleanup that cannot restore the agent config must keep it and fail. Copies of the harness with one guard removed (a `run_denied` wrapper, the stopped-services flag, the cleanup restore, cleanup's own log, the external terminal write) or with one launchd label form hardcoded must fail; under macOS `/bin/bash` 3.2 so must copies without the TERM or HUP trap, without signal ignoring during the restore, or without leaving the stage log. What CI proves is the guard logic, classification of recorded outcomes and the signal tests under bash 5; the SBPL semantics and the bash 3.2 behaviour those signal guards exist for are proven only where the verifier runs on macOS, where it also runs the preflight against the real `sandbox-exec` with every mutant, and on the M1 hardware run. Every probe socket is pinned to `lo0`, so nothing leaves the host. |
| `verify_jetson_lifecycle.sh` | Syntax-checks and shellchecks the native Jetson lifecycle harness `tools/validation/jetson-lifecycle.sh`, checks that it runs all eight canonical stages — with upgrade and rollback also reachable as reasoned skips when no baseline set is given — that offline falls between crash-loop and upgrade, and that it records the artifact digest after install, and that its bundle staging path is visible to the agent unit's sandbox. Drives each preflight refusal through seams (required commands, `tensorplate` group membership, architecture, Ubuntu 22.04, L4T R36, tag and manifest binding, checksums and digest, inputs under directories the run deletes, bundle build before purge) and runs every exercised stage against a stubbed appliance. Each stage assertion and each privileged step is made to fail on its own, and the case checks that the stage records `fail`, that its log gives that reason, and, where a later check would also fail, that the stage stopped at the first failure. Package inventory failures before and after purge must stop state deletion. Hostile operator CLI configuration cannot redirect the calls, and an inference endpoint differing from the active deployment must fail the round trip. Crash-loop config restoration is checked on restore, recovery and backup failures and on signals, with the harness started under default signal dispositions. The offline stage is driven against a stubbed systemd: a `systemd-run` that runs the command it was given and records whether the denial properties reached it, a unit tree whose loaded configuration and start generations are tracked apart — so a reload that never reached a running instance is distinguishable from one that did — and a probe fixture that answers the way the kernel does under systemd's address filter, with its allow list taken from the properties the harness actually passed rather than from a list kept here. Read off a clean run: both services denied through runtime drop-ins and nothing under `/etc`, every drop-in removed and read back as removed, the allow list exactly `127.0.0.1/32` and `::1/128` with the `localhost` shorthand refused, all five CLI calls made inside their own denied transient unit behind the module's `run-denied` probe of that unit and pinned to the private CLI config, the control taken before anything was denied, each service probed inside its own control group against its own control, the certificate's verdicts re-derived from the documents it carries, and the certificate passing the evidence publication scanner. Because this row has no metadata service, every probe must be taken with `--metadata-address none` — the fixture refuses one that is not — and every classification with `--metadata-operation absent`, so an operation that vanished from a document cannot read as one that passed; nothing the harness runs may name the Compute Engine row's machine-type record. Each way the stage could certify a device it did not deny, an identity it did not establish, an appliance that stopped working, or a device it did not put back is driven on its own — an inert or shorthand or extra-directive drop-in, a dead unit, a persistent copy under `/etc`, a restart systemd ignored on either side, a removal the device ignored, a leftover from an earlier run per unit including a dangling symlink, a probe that leaks, crashes in a service's control group or in a CLI call's own unit -- where the call must never be run -- or runs in a unit systemd did not filter, a control refused or never sent, an unreachable agent socket, doctor naming a GCE machine type or losing the L4T release, an agent claiming a live metadata answer or a record written while denied, an agent reporting another deployment as active after the denied deploy, and a garbled inference — and each must record `offline` as a failure, stop at the named step for the named reason, and still leave the network policy as it found it. Each privileged command the stage takes is failed on its own too — the drop-in install, the reload, the journal capture, `systemd-run`, the in-service control and probe, the deny-side restart, and the cleanup's removal, reload and restart — with the commands earlier stages also take narrowed to this stage's side of the denial. Preflight refuses a device without `systemd-run`, a harness copied out of the checkout without the offline module beside it, a leftover drop-in per unit, and a `--deployment-id` any of whose derived forms -- `-offline`, `-baseline`, `-rollback` -- would pass the CLI's 128-byte limit, as well as one that leaves the charset or is a reserved path segment; the boundary cases are one byte apart, so a guard that bounded only the shortest derivation fails here. Every transient unit the stage starts is read back as the operator's own, with the operator's groups and with `--pipe --wait --collect`, so a call that would run as root on a device cannot pass. Every journal capture is projected to the service's own fields where it is taken: the projected files pass the publication scanner, the stub journalctl's own unprojected output is refused by it, the harness's kept-field set is compared against the scanner's, and no raw capture survives the run. With a baseline set it also drives the upgrade and rollback stages against a fixture installer and a per-package dpkg database, conffile and durable state that move with each install, purge and removal, where a removal changes only the packages it names and the installer refuses a downgrade over a package the removal left: the baseline's eligibility (both options together, the pinned `v0.1.5` tag, a candidate newer than it, every runtime package strictly older by a real `dpkg --compare-versions` stub rather than one that answers 0, compared on each `.deb`'s control `Version` and not on the manifest's file-name-derived one, a `.deb` `dpkg-deb` cannot read, a manifest that declares a Debian version for each package, non-snapshot manifest, checksums and the baseline's own digest), a run environment carrying any `TP_INSTALL_*` variable, the four installs in order with the upgrade's and rollback's three behind the harness's real environment scrub — which must hold when sudo itself hands the installer `TP_INSTALL_ALLOW_UNSIGNED` — each refusing a set whose `SHA256SUMS` changed after preflight and an install that did not print the verified-signature line, the services coming up after each of the three, the baseline's own deployment round trip, the operator conffile edit surviving both directions, new service pids across the upgrade, the baseline's deployment re-warming with no deploy of the harness's own, a removal that leaves each conffile-owning package in `config-files` — a purged one is caught whether dpkg drops its record or keeps it `not-installed` — leaves nothing else `installed` or `half-configured`, and leaves `tensorplate-apt-source` as it was, including on a device that never had it, the rollback's preconditions checked before anything is stopped, set aside or removed, the set-aside state held to the digests taken from the stopped agent's own directory before the move rather than to a pathname in it — the fixture state directory holds the three files a device holds, the agent's `state.json` and `state.json.bak` and the observability snapshot, and any of them emptied, truncated, rewritten at the same length, deleted, or joined by a file that was not set aside fails the stage and names it; a set-aside directory that is there and holds nothing fails naming the directory, a durable state directory without `state.json` is refused before the move, and a privileged listing or digest that fails stops the rollback with nothing yet moved, reported as unread rather than as changed — the older agent reporting no deployment, a failing doctor on the baseline recorded rather than asserted, the upgrade's clearing failing on a purge, a leftover package and a failed query, and cases that fail with `PYTHONOPTIMIZE` set. In every window where the device serves nothing, the stranded-device report must be filed and printed, and must name what dpkg lists when it is written (including packages an installer that failed late left installed), whether the baseline installer ran, whether the conffiles were read as kept, and where durable state is — and where it was set aside, whether what is behind that pathname still matches the digests taken before the move, which is checked against an install that destroys the set-aside state and then fails late, the one shape that reaches the report without reaching the stage's own check; outside those windows it must not appear, and a terminal that goes away inside one must not stop the lifecycle report. The hardware run itself is manual. |
| `verify_descriptor.sh` | Validates the shipped backend descriptor against the JSON schema using `jq` (or falls back to a structural check). |
| `verify_descriptor.sh` | Validates the shipped backend descriptor's required fields, absolute interpreter path, and that its declared `tensorplate_runtime_range` both admits the release line this tree targets and brackets `packaging/VERSION`. The descriptor is not rewritten by the release driver on a version bump, so this is what makes the drift loud. |
| `verify_arch_package_set.sh` | Runs `dpkg-buildpackage -B` with stub ELF binaries and asserts debhelper emits exactly the five arch-dependent runtime packages for the host architecture, leaves the three `Architecture: all` packages to the primary build, keeps the metapackage payload-free, ships the serving binary from the package, and that the release job's copy globs exclude auto-generated `-dbgsym` packages. Not in `run.sh`: it writes `.deb` files to the repository parent. |
| `verify_installer.sh` | Syntax-checks `packaging/scripts/install.sh`, runs `shellcheck` when available, and exercises installer self-check, supported OS, unsupported OS, `--force-os`, hardware warning, `--strict-hardware`, and `--cli-only` paths with fixtures. |
| `verify_service_supervision.sh` | Drives the shipped systemd units against a real systemd: the agent reaches active and logs to the documented path, a hard crash is recovered, a crash LOOP is given up on rather than restarted forever, a clean stop is not restarted, observability survives the agent stopping, and no serving unit is registered. Mutates the host; refuses to run unless `CI=true` or `TP_SUPERVISION_ALLOW=1`. Not in `run.sh`. |
| `verify_cpu_only_smoke.sh` | The Ubuntu x86_64 CPU-only Preview smoke, and the only check that installs REAL binaries and runs the REAL CLI: builds the runtime, installs the package set, asserts package closure and the x86_64 agent config, confirms the installed registry reports the row as Preview, starts the agent and observability, requires a GREEN `tensorplate doctor` that resolves the row by live detection with no Production claim and whose `agent_socket` finding names the socket from the packaged `/etc/tensorplate/cli.json` rather than the built-in default (the evidence line from issue #203, and the only check that tells a CLI that reads the conffile from one that ignores it), queries the control plane, and requires `tensorplate logs` either to exit `6` naming the journal to read instead, or to exit `0` having returned entries or said why it returned none. Writes evidence under `dist/smoke/`. Mutates the host; refuses unless `CI=true` or `TP_CPU_SMOKE_ALLOW=1`. Not in `run.sh`. |
| `run.sh` | Orchestrator. Runs every verifier except the host-mutating `verify_arch_package_set.sh`, `verify_service_supervision.sh`, and `verify_cpu_only_smoke.sh`, and exits non-zero on the first failure. Takes an optional group: `core` (the packaging, installer, descriptor and harness-drift checks, which the release artifact build runs), `harness` (the five lifecycle harness verifiers, which CI runs as their own job because they take far longer), or `all`, the default. A `verify_*.sh` that is in no group and not listed as host-mutating fails the suite before anything runs. |
| `run_groups_test.sh` | Tests `run.sh` against stub verifiers: each group runs exactly its own verifiers in order, host-mutating verifiers never run, an unknown group is a usage error, a verifier in no group fails the suite, a failing verifier stops it with its status, and every verifier `run.sh` names exists. |

## Running

```bash
# Single command runs the full suite. Returns 0 on green.
./test/packaging/run.sh

# Or run an individual verifier.
./test/packaging/verify_layout.sh
```

The suite does not require root: every check operates on the source
tree or stages under `mktemp -d`. It runs on macOS dev hosts (no
systemd present) and on Linux CI hosts.

## What is NOT verified here

- Actual `.deb` artifact build (`dpkg-buildpackage`). The skeleton is
  build-system-ready but the upstream Rust + C++ binaries are not
  staged on host CI yet — `dpkg-buildpackage` runs on the release validation
  Jetson target.
- Live `systemctl enable --now`. That happens on the release validation target
  device, with output captured in
  `docs/install/clean-install-runbook.md`.
- CUDA / TensorRT / LibTorch functional checks. F06 doctor probes
  cover artifact presence; functional validation belongs to release validation.
